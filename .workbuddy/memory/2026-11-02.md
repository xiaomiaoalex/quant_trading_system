## Paseo 独立测试员启动被审批额度阻塞：根因与处置

- **现象**：`feat/foundation-refactor` 阶段 2 要启动独立测试员，`create_agent` 报 `Automatic approval review failed due to usage limit / action was not executed`。后来连 `list_profiles`、`list_models`、`inspect_provider` 这类只读工具也全部失败。
- **排查关键**：`~/.codex/config.toml` 里 `model = "group/official-first"`，**没有** `approvals_reviewer`、也没有 `approval_policy`（全省略即默认）。该组由 magpie 以 `order` 策略实现（codex → kimi）。会话截图显示 `Shell git branch --show-current` 正常执行，而紧随其后的 4 个 MCP 工具调用全部告警失败。
- **机制结论（可复用）**：沙箱内允许的命令不走审批，MCP 工具调用必须过审批。审批审查是运行时发起的**独立模型调用，携带具体模型 id 而非 `group/official-first` 虚拟组名**，因此不命中路由组，magpie 的 order 兜底不生效，请求落到额度已空的 codex；审批判定失败是 **fail-closed**，直接拒绝而非降级放行。**路由组覆盖的是生成通道，不是审批通道**——这是"provider 有额度、组有 fallback，仍不能执行"的原因。
- **评估过的替代方案**：`approvals_reviewer = "user"`（审查数量升、信息质量降，易审批疲劳，破坏 `polling:false` 无人值守）；追加 `approval_policy = "on-request"`（若原为 never/full-access 会反向收紧，反而让 shell 也弹审批）；关闭审批/full-access（仓库有 git 与写权限，不成立）；`[auto_review]` 指定审查模型（文档提到该段但本机是否支持未证实）。另：手改 config.toml 会被 magpie Drift 检测覆盖。
- **决策（13:44）**：用户选择重置额度，不改任何审批配置。状态维持 `BLOCKED`，第 1 轮审核失败保留，该阻塞**不计为测试失败**。
- **落盘**：`docs/FOUNDATION_AGENT_WORKFLOW.md` 新增 7.2 节；`docs/FOUNDATION_WORKFLOW_STATE.json` 的 blocker 增 `root_cause` / `rejected_options` / `decision` / `recovery_steps`（5 步），JSON 已校验。
